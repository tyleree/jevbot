# Completeness critique of the build brief

Produced by an independent critic agent on 2026-09-17. Where this file and `01-build-brief.md` disagree, THIS FILE WINS.

## Gaps (with researched resolutions)

### G1. [BLOCKER] Go/no-go rests on Tier A forward paper trading, but the brief never quantifies how long that takes, and it conflicts with the brief's own finding that pinned Jev versions get de-listed within weeks (section 1.11: no deprecation policy; section 7.1: 'any version change is a new experiment').

Researched the Minimum Track Record Length formula in the primary paper (Bailey and Lopez de Prado). The code listing in the paper reads verbatim `minTRL=1+(1-stats[2]*sr+(stats[3]-1)/4.*sr**2)*(norm.ppf(self.prob)/(sr-self.sr_ref))**2`, and the paper states 'MinTRL is expressed in terms of number of observations' and gives the worked example 'a 2.73 years track record is required for an annualized Sharpe of 2 to be considered greater than 1 at a 95% confidence level' (daily IID Normal returns). My own computation with that formula (computed, not quoted): true annual Sharpe 1 vs 0 at 95% needs about 684 daily observations, roughly 2.7 years; Sharpe 2 vs 0 needs about 173 days, roughly 0.7 years; with short-premium style skew -1.5 and kurtosis 8 (my assumption) Sharpe 1 needs about 3.0 years. Calibration metrics do not rescue this quickly either: with three highly correlated ETFs and a 15-session horizon there are only about 17 non-overlapping windows per year (inferred). Meanwhile the vendor has already de-listed jev-1.12 and publishes no deprecation policy, so a pinned jev-1.13.0 forward test is unlikely to survive long enough, and any successor model's training cutoff may swallow the earlier forward window (turning that Tier A data into Tier C for the new model). This needs a user decision before code: (1) pre-register what happens on a forced model change (shadow-run old and new in parallel while both exist, measure decision agreement, define an agreement threshold for continuing the same experiment versus restarting); (2) add short-horizon (1 to 5 session) machine-resolvable calibration questions purely for evaluation so resolved outcomes accumulate faster; (3) accept explicitly that a P&L-based verdict is a multi-year exercise and make calibration versus option-implied probability the primary pre-registered endpoint.

Sources: https://www.davidhbailey.com/dhbpapers/sharpe-frontier.pdf ; https://docs.typesafe.ai/models.md

### G2. [MAJOR] Contradiction between the backtest fill model (section 7.3, ORATS fills inside the spread at p=0.66 for two legs) and how Alpaca paper actually fills (section 4.2). The brief calls paper fills 'optimistic' and tells us to haircut paper P&L, which is one-sided.

Alpaca's paper doc says verbatim: 'Orders are filled only when they become marketable. This means that a non-marketable buy limit order will not be filled until its limit price is equal to or greater than the best ask price, and a non-marketable sell limit order will not be filled until its limit price is equal to or less than the best bid.' and 'Your order quantity is not checked against the NBBO quantities... they will receive partial fills for a random size 10% of the time.' So paper is optimistic on size and queue but pessimistic on price: a spread limit placed inside the natural market (the ORATS assumption) will simply not fill in paper until the limit reaches the natural price. Paper P&L therefore corresponds to the backtest's worst-case band (buy at ask, sell at bid), and adding a further cost haircut double counts. The doc says nothing about options or multi-leg orders specifically, so how net-price marketability is computed for mleg orders is still unknown and must be tested. On the quote source: Alpaca staff (Dan Whitnable, forum, 2025-09-12) said of the indicative feed 'This returns option data based upon real time OPRA data but it's randomized a bit. It's not real data and should not be used for live trading' and 'If one is using the free Basic subscription then due to licensing real time OPRA data is not available'; the docs say 'the quotes are not actual OPRA quotes, they're just indicative derivatives. The trades are also derivatives and they're delayed by 15 minutes.' No staff statement says which feed drives paper option fills; one forum user concluded empirically it is 15 minutes delayed (unconfirmed). Recommendation (inferred): treat Alpaca paper fills as a plumbing test only; compute Tier A P&L from shadow fills using our own fill model on recorded quotes, report the worst-case band as the number comparable to Alpaca paper, and make fill-independent calibration metrics the primary endpoint.

Sources: https://docs.alpaca.markets/us/docs/paper-trading.md ; https://forum.alpaca.markets/t/paper-trading-options-pricing/17795 ; https://docs.alpaca.markets/us/docs/historical-option-data.md

### G3. [MAJOR] Section 3.5's runtime policy (draw K=3 samples of the same input and require agreement) assumes identical requests give independent draws. That is unverified, and the brief's own section 0.4 says so. The per-question cache key in section 3.6 has a related dependency on batch independence that was measured only on jev-1.12.

Confirmed in the vendor's noul consistency cookbook: the TypeSafe call used `state={"uid": f"{sample_index}:{token_hex(4)}", "claim": CLAIM}` and the page states verbatim 'This setup cannot separate sensitivity to the irrelevant field from variation that would occur on identical requests.' Nothing in the docs says whether byte-identical requests are deterministic or server-cached. If they are deterministic, K identical samples is a no-op that adds cost and false reassurance; if we add a uid to force variation we break the brief's own 'no uid in state' cache rule. This cannot be resolved without a live key. Recommendation (inferred): make Step 0 a hard gate before any threshold work, and design the robustness check around deterministic, meaning-preserving perturbations instead of repeats: permuted Choice option order, permuted state key order, and a bucket-only versus value-plus-bucket rendering. Each variant is content-addressed, so the cache needs no `sample` index and replays stay bit-reproducible. Also in Step 0, verify on jev-1.13.0 that a question's answer is unchanged when batched with different sibling questions; until then key the cache on (state, full question-set hash, question) or always send the full batch, because 'send only the missing questions' changes batch composition.

Sources: https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook.md

### G4. [MAJOR] Time-of-day and expiry policy is hard-coded to a normal session (decide near 15:45 ET, close everything 'well before 15:30 ET on the last trading day') and cannot be simulated with one EOD snapshot per day. Early-close days, the 16:15 ET close of SPY/QQQ/IWM options, and the market calendar source are all missing.

NYSE hours page (via WebFetch summary): remaining 2026 early closes are Friday 2026-11-27 and Thursday 2026-12-24, with the footnote 'Each market will close early at 1:00 p.m. (1:15 p.m. for eligible options)'; 2027 early closes include 2027-11-26 and 2027-12-24. On those days a 15:30/15:45 ET rule fires after the close. Alpaca's expiry text says only 'Starting at 3:30 pm EST on the date of expiration, Alpaca continuously evaluates any open positions that expire that day and stops accepting new orders to open/extend any positions' and says nothing about early-close days. SPY, QQQ and IWM have daily expirations, so every early-close day is an expiry day. Calendar source: `GET /v2/calendar` ('the response also contains the specific open and close times for the market days, taking into account early closures'; fields `date`, `open`, `close` in HH:MM, `session_open`, `session_close`, `settlement_date`) and `GET /v2/clock`. In alpaca-py 0.44.0 these are `TradingClient.get_calendar()` and `get_clock()`; note `Calendar.open`/`close` are parsed with `datetime.strptime(..., "%Y-%m-%d %H:%M")` so they are naive Eastern datetimes, while `Clock` has `timestamp`, `is_open`, `next_open`, `next_close`. Alpaca's docs describe day orders as valid 9:30am to 4:00pm ET; I found no Alpaca statement that option orders are accepted between 16:00 and 16:15 ET, so assume they are not. Recommendation (inferred): replace the clock-time rule with 'never hold any position into its expiration day: exit at the last decision snapshot with DTE >= 1', express all cut-offs as offsets from that day's calendar `close`, and stop submitting orders 5 minutes before it. That rule is simulable on EOD data, identical in paper, and sidesteps the undocumented 3:30 pm process, the issue #774 short-leg report and the early-close ambiguity.

Sources: https://www.nyse.com/markets/hours-calendars ; https://docs.alpaca.markets/us/reference/legacycalendar.md ; https://docs.alpaca.markets/us/docs/options-trading-overview.md

### G5. [MAJOR] Broker client safety: the brief does not mention that alpaca-py has no HTTP timeout, that it retries order POSTs, or that orders need an idempotency key for crash and retry safety.

Read alpaca-py at tag v0.44.0. `alpaca/common/rest.py` calls `response = self._session.request(method, url, **opts)` where `opts` holds only `headers` and `allow_redirects: False` (plus params/json); the word 'timeout' does not appear in the file, so every REST call can block forever on a hung socket, including the exit path. The retry loop (`while retry >= 0: ... except RetryException: time.sleep(self._retry_wait)`) applies to every method including POST, with `DEFAULT_RETRY_ATTEMPTS = 3`, `DEFAULT_RETRY_WAIT_SECONDS = 3`, `DEFAULT_RETRY_EXCEPTION_CODES = [429, 504]`. A 504 on `POST /v2/orders` can mean the order was accepted, so a blind retry can double-submit. The order API documents `client_order_id` as 'A unique identifier for the order. Automatically generated if not sent. (<= 128 characters)', and the SDK has `get_order_by_client_id`. Recommendation (inferred): set a deterministic `client_order_id` derived from (decision_id, action, attempt) on every order including mleg parents; on any ambiguous failure look the order up by client id before resubmitting; wrap broker calls with an enforced timeout (for example run them in a worker with a deadline, or wrap `client._session.request` with a default `timeout=(3, 10)`); that a duplicate client_order_id is rejected is implied by 'unique' but should be confirmed in paper.

Sources: https://raw.githubusercontent.com/alpacahq/alpaca-py/v0.44.0/alpaca/common/rest.py ; https://docs.alpaca.markets/us/reference/postorder.md

### G6. [MAJOR] The kill switch and risk limits are named in the pipeline but never specified: no triggers, no numeric limits, no broker-side actions, no statement of what happens to open spreads.

Broker primitives verified in alpaca-py 0.44.0 and the Alpaca reference: `TradingClient.cancel_orders()`; `close_all_positions(cancel_orders=True)` whose docstring says 'Places an order for each open position to liquidate'; and `set_account_configurations(...)` with `suspend_trade` documented as 'If true, new orders are blocked.' plus `max_options_trading_level` ('0=disabled, 1=Covered Call/Cash-Secured Put, 2=Long Call/Put, 3=Spreads/Straddles'). Caveats found: `close_all_positions` closes leg by leg, so a credit spread's long leg may be closed first and the remaining short rejected or left uncovered; unpriced closes are market orders and the error table lists 'options market orders are only allowed during market hours'; `suspend_trade` blocks closing orders too, so it must be the last step; the Replace error table includes '403 40310000 replace mleg order is disabled', so repricing a spread must fall back to cancel and resubmit. Broker-side limits also exist: 'options order qty must be <= {max}', 'options order notional is {n} must be <= {limit}', 'exceeded account limit for contracts expiring today'. Recommended kill-switch sequence (inferred): stop the decision loop, cancel all orders, close each structure with one mleg order using *_to_close intents (shorts first if legs must go separately), verify flat via positions, then set suspend_trade=true, and require a manual file or flag to re-arm. Suggested starting triggers (my recommendation, not from a source): daily loss over 2% of equity, drawdown over 8%, max defined loss per trade 1%, aggregate open max-loss 10%, max new positions per day, max orders per minute, any reconcile mismatch between ledger and broker positions, stale quotes or clock, repeated Jev or broker errors, and resp.model mismatch. The user still has to confirm the numbers (brief question 4).

Sources: https://docs.alpaca.markets/us/reference/getaccountconfig-1.md ; https://docs.alpaca.markets/us/docs/options-trading-overview.md

### G7. [MAJOR] Paper-only enforcement is reduced to 'hard-code paper=True' and a base-URL check; the brief does not establish what actually prevents a live order.

Alpaca's authentication doc states: 'If you have more than one account... each of those have separate credentials. As an example, you cannot use your live account's credentials with the paper API, or vice versa.' Paper trading lives on `paper-api.alpaca.markets`, live on `api.alpaca.markets`. Alpaca's 2026-09-14 key-security article says 'While Paper keys often begin with a `PK...` prefix and Live keys with an `AK...` prefix, these prefixes are visual hints' and 'a paper key pair will be rejected with an `HTTP 401 Unauthorized` error if sent to the live brokerage endpoint... The authoritative security boundary is the host environment itself.' In alpaca-py 0.44.0 the base URL is `url_override if url_override else BaseURL.TRADING_PAPER if paper else BaseURL.TRADING_LIVE`, stored as `client._base_url`; the TradingClient constructor does not read an environment variable for the URL. The strongest control is structural: use an Alpaca 'Paper Only Account' (the docs say anyone can create one with an email), so no live credentials exist at all. Layered controls (inferred): construct TradingClient and TradingStream in exactly one module with paper=True as a literal and never pass url_override; assert at startup that `_base_url` equals the paper URL and refuse to start otherwise; treat a key not starting with PK as a startup error (hint only); name the env vars ALPACA_PAPER_KEY / ALPACA_PAPER_SECRET; add a test and a grep-based CI check that fails on the strings 'api.alpaca.markets' (without the paper- prefix), 'paper=False' and 'url_override'.

Sources: https://docs.alpaca.markets/us/docs/authentication.md ; https://alpaca.markets/learn/api-key-security-best-practices-for-alpaca-builders

### G8. [MAJOR] Section 7.5 requires closing short ITM calls before ex-dividend dates, but the brief names no source for ex-dates and dividend amounts. It also assumes one assignment and dividend policy for backtest and paper, while paper does not simulate those events.

Source found: Alpaca Market Data `GET /v1/corporate-actions` with `types=cash_dividend`, returning `ex_date`, `record_date`, `payable_date`, `rate`, `special` per event; start and end filter on `process_date`. In alpaca-py 0.44.0 it is `alpaca.data.historical.corporate_actions.CorporateActionsClient.get_corporate_actions(CorporateActionsRequest(symbols=[...], types=[...], start=..., end=...))`, limit default 1000. ### G9. [MAJOR] Design-level gap: with the section 6.2 state, almost every field Jev sees is a label our code already computed ('iv_rich: implied clearly above recent realized', trend direction 'up'), and the questions ask Jev to restate them (vol.richness, under.direction). The brief does not say what information Jev adds beyond the deterministic rule baseline, and news, the only free-text input, is optional in v1 (question 8).

This is my inference, not a sourced fact. The vendor's guidance supports the concern: the jaggedness page says to avoid 'Asking the model something code can compute exactly' and that Jev is for 'the part that is genuinely a judgment'; the composite-scoring pattern says to combine atomic answers with weights in code. If v1 ships buckets-only, Jev is close to a noisy lookup on our own labels, and baseline 5 (transparent rule on the same buckets) should match it; the experiment then cannot show Jev adds anything and the leakage machinery protects nothing of value. Recommendation: pre-register an ablation 'Jev on buckets-only versus deterministic mapping of the same buckets' and expect near-zero difference; concentrate Jev questions on inputs code cannot judge (masked headline text, event descriptions, thesis-versus-news consistency); and decide question 8 with this in mind, since without text there is little to test. Also specify how entity masking is done (the brief names no tool or rule set), because for index-ETF news the informative tokens (central bank, inflation print) are exactly what masking removes or what lets a model re-identify the date.

### G10. [MAJOR] Operations on a WSL2 desktop are not covered: the bot must be running at specific market times, but WSL2 shuts idle VMs down and its clock drifts after host sleep. There is also no dead-man control if the process is down on an exit day.

Microsoft's WSL config doc gives `vmIdleTimeout` default `60000` ('The number of milliseconds that a VM is idle, before it is shut down', Windows 11 only) and, under `[general]`, `instanceIdleTimeout` default `15000` ('The number of milliseconds that a distro is idle, before it is shut down. Set to -1 to disable auto shutdown'); systemd is enabled with `[boot] systemd=true` in /etc/wsl.conf. Clock drift after sleep or hibernate is a long-running open problem: microsoft/WSL issues #5324, #8204 and #13867 ('WSL 2 (Ubuntu 24.04): Time/Clock Drift'), with drift reported from minutes to hours; workarounds are `sudo hwclock -s` or a resume-triggered task. Recommendations (inferred): run the bot as a systemd service with restart-on-failure; set instanceIdleTimeout=-1 and disable Windows sleep during market hours; never use the local clock for trading decisions, instead take time from Alpaca `get_clock().timestamp` and refuse to trade if local and broker time differ by more than a few seconds; on startup always reconcile positions and open orders from the broker before deciding anything; add an external heartbeat alert; and keep every open position defined-risk with a GTC closing order or an exit at DTE >= 1 so that a dead process cannot carry a position into the expiry-day auto-liquidation window. The machine also shares one GPU with other workloads, which does not matter for Jev (remote API) but matters if the LLM-adapter control arm is ever run on a local model.

Sources: https://learn.microsoft.com/en-us/windows/wsl/wsl-config ; https://github.com/microsoft/WSL/issues/13867

### G11. [MINOR] Section 7.3 says 'add per-contract commissions and regulatory fees' but gives no numbers.

## Corrections to the brief

1. Section 4.1 says the paper options level is unknown. Resolved: Alpaca's Level 3 launch post (2025-02-25) states 'All paper trading accounts will automatically have access to Level 3 strategies.' Keep the startup assertion anyway. Source: https://alpaca.markets/blog/level-3-options-trading-now-available-with-alpacas-trading-api/

2. Section 1.11 says to verify on the first live call whether resp.model carries the versioned id. It is documented: models.md says 'The response's `model` field reports the versioned ID that answered', and both consistency cookbooks request `TYPESAFE_MODEL = "jev-latest"` and print 'TypeSafe returned models (calls): {'jev-1.13.0': 15}'. The api.md samples that echo the alias are illustrative. Source: https://docs.typesafe.ai/models.md

3. Section 1.9 calls the token budgets conflicting. They read as two limits rather than a contradiction: the jev-1.13 jaggedness page gives '64k tokens together for all `state` and `questions`' and '32k tokens for the `state` + the longest `question`', explaining that Jev 'ingests the state and then processes all the questions in parallel'; primitives.md's 'around 32,000 tokens, roughly 150,000 characters' is the general statement. Designing to 32k total remains safe. Source: https://docs.typesafe.ai/model-jaggedness/jev-1.13.md

4. Section 4.2 says to match Alpaca errors on code and HTTP status, never on message text. The documented error tables use one code per status for dozens of different conditions: 403 / 40310000 covers 'account not authorized to trade options', 'insufficient options buying power', 'exceeded account limit for contracts expiring today' and 'replace mleg order is disabled'; 422 / 42210000 covers every validation failure. Code plus status can only classify coarsely (rejected, do not retry). Distinguishing a buying-power rejection from an authorization failure requires the message text, so log it and use substring matching for diagnostics only. Source: https://docs.alpaca.markets/us/docs/options-trading-overview.md

5. Section 4.2 'Paper fills are optimistic' and 'apply our own cost haircut to paper P&L' is one-sided. Per Alpaca's paper doc, limit orders fill only once marketable against the best bid or ask, so paper is pessimistic on price (full spread crossed) and optimistic only on size and queue. A haircut on top double counts; the comparable backtest number is the worst-case band, not the ORATS headline. Source: https://docs.alpaca.markets/us/docs/paper-trading.md

6. Section 4.2 / 4.3 sign convention is right (API reference: 'A positive value indicates a debit... A negative value signifies a credit'), but note a trap in the Alpaca Level 3 guide: its iron condor example (buy 190P, sell 195P, sell 205C, buy 210C, a credit structure) uses `"limit_price": "1.80"`, i.e. a positive debit limit. Do not copy that example's sign. Source: https://docs.alpaca.markets/us/docs/options-level-3-trading.md

The PyPI description says authentication is by email and password: a default `./creds.txt` (email on line 1, password on line 2), explicit `ThetaClient(email=..., password=...)`, or the `THETADATA_CREDENTIALS_FILE` env var. It lists 'An active ThetaData subscription' as a requirement (whether FREE qualifies is still unknown) and the default dataframe output is Polars; pass `dataframe_type="pandas"` for pandas. Source: https://pypi.org/project/thetadata/

PyPI upload times show 0.0.1a0 on 2026-09-09, 0.5.7 on 2026-09-11 and 0.6.0 on 2026-09-15, so 0.6.0 followed the previous public upload by four days. 10. The brief never mentions the PDT change behind the 2026-07-06 API break. Alpaca's changelog says PDT and day-trading buying power fields 'are deprecated and will be removed on 2026-07-06' (`daytrade_count`, `daytrading_buying_power`, `dtbp_check`), tied to FINRA replacing the pattern day trader rule with an intraday margin framework ($25,000 threshold and four-trades-in-five-days count eliminated; a 12-month transition during which firms may apply either regime). With the default $100k paper balance this does not constrain the bot, but do not write code against the removed fields, and note that short option sales and long option expirations are classed as 'IML-reducing' transactions under the new rule. Source: https://docs.alpaca.markets/us/docs/understanding-finras-new-intraday-margin-rule-and-the-end-of-pdt.md
